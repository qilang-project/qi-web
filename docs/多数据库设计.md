# qi 多数据库支持设计（SQLite / PostgreSQL / MySQL）

2026-08-10 起草。目标：让 qi-web 与 qi 应用能连 PostgreSQL 和 MySQL，
**而现有代码一行不改**。

---

## 一、现状

qi 的数据库能力是一层薄 FFI，实现锁死在 SQLite（`rusqlite`，bundled）：

| 层 | 位置 | 状态 |
|---|---|---|
| 查询构建 / 仓储 / 迁移 | `qi-web/查询.qi`、`仓储.qi`、`迁移.qi` | 已有，与后端无关 |
| **统一驱动接口** | **不存在** | ← 本设计要补的那一层 |
| 驱动 | `qi/src/runtime/stdlib/database_ffi.rs`（591 行） | 只有 SQLite |

对外 14 个函数（`qi-runtime/src/stdlib/database_ffi.rs` 是 `include!` 同一份，**改一处即可**）：

```
数据库.连接(路径) -> 句柄            数据库.关闭(句柄)
数据库.执行(句柄, SQL)               数据库.查询(句柄, SQL) -> JSON 行数组
数据库.执行参数(句柄, SQL, 参数JSON)   数据库.查询参数(句柄, SQL, 参数JSON)
数据库.开始事务/提交/回滚(句柄)         ← 连接级
数据库.开启事务(句柄) -> 事务句柄       ← 事务对象级
数据库.事务执行参数/事务查询参数/提交事务/回滚事务
```

消费方：`项目/` 下 12+ 个应用（家有小奇、看板、健身房、有声绘本…）、qi-web 自身
（会话、指标、仓储）。

### 现有设计里已经做对的一件事

**查询结果是 JSON 行数组**，这等价于 Go `database/sql` 的 `driver.Value` 窄腰
（只允许 6 种类型，复杂类型由驱动降级）。PostgreSQL 那几十种类型
（numeric / uuid / jsonb / timestamptz / 数组）**不需要扩接口**，按保守规则降到
JSON 基本类型即可。这条决定了本设计不必改动 FFI 签名。

---

## 二、设计原则（来自其它语言的教训）

| # | 原则 | 依据 |
|---|---|---|
| 1 | **占位符由中间层翻译**，对外永远 `?` | JDBC / PDO 这么做；Go `database/sql` 和 Python DB-API 把方言暴露给用户（`$1` vs `?`、`paramstyle`），公认是败笔 |
| 2 | 连接池在中间层，不在驱动 | Go stdlib 统一池化；JDBC 不管，导致每个项目自己选 HikariCP |
| 3 | **DDL 方言不在驱动层抹平**，推到迁移层 | Rails / Django / Flyway / Alembic 无一例外 |
| 4 | 类型收窄成窄腰，驱动负责降级 | Go `driver.Value` 靠这个稳定了十几年 |
| 5 | 不做编译期 SQL 校验 | sqlx / diesel 宏要求构建时连真库，会卡死本项目的 Mac→Linux 交叉编译与 CI |

原则 1 是本设计成立的关键：现有代码里 45 处 SQL 全用 `?`
（`VALUES (?, ?, ?)`、`WHERE 用户id = ?`），翻译放在中间层，它们**一行都不用改**。

## 三、架构

```
        应用 / qi-web 仓储·查询·迁移        ← 不改
                    │  数据库.连接("postgres://…")
        ┌───────────▼────────────┐
        │  中间层（新增，Rust）      │  按 URL scheme 分发
        │  · 方言翻译 ? → $n       │  · 连接池 · 类型→JSON 降级
        └──┬─────────┬──────────┬─┘
      rusqlite   postgres     mysql          ← 三个同步 crate
```

**后端选型：`postgres` + `mysql` 两个同步 crate。**
理由是与现有阻塞式 FFI 模型（rusqlite 同步 + `Mutex` 连接表）天然一致，
不引入 async 传染。`sqlx` 一库通吃很诱人，但异步优先，每个 FFI 都要 `block_on`
并管理 runtime 句柄，与现有语义打架。

```rust
enum 后端 {
    SQLite(rusqlite::Connection),
    PG(postgres::Client),
    MySQL(mysql::Conn),
}
```

`ConnectionState` 把 `conn` 字段换成 `后端`，其余（连接表、事务表、id 分配）不动。

### 连接串

```
绘本.db                        → SQLite（**保持旧行为**，无 scheme 即文件路径）
sqlite://path/to.db            → SQLite（显式形式）
postgres://user:pw@host/db     → PostgreSQL（postgresql:// 同义）
mysql://user:pw@host/db        → MySQL
```

`数据库.连接` 签名不变（仍是一个字符串），旧调用全部继续有效。

## 四、三个真问题与解法

### 4.1 占位符方言（必须解决）

SQLite / MySQL 用 `?`，PostgreSQL 只认 `$1 $2`。中间层在发往 PG 前改写。

**不能无脑替换** —— 要跳过字符串字面量、注释、以及 PG 的 `::` 类型转换和
`?`/`?|`/`?&` jsonb 运算符。实现为一个小状态机：

```
逐字节扫描，维护状态：普通 / 单引号串 / 双引号标识符 / 行注释 / 块注释
仅在「普通」状态下遇到 ? 时替换为 $n（n 递增）
'' 转义（SQL 标准的引号内双写）要正确跨过
```

这是本设计**唯一需要单元测试重点覆盖**的部分（含 `'it''s ?'`、`--` 注释、
`/* */`、`a::text`、jsonb `?` 运算符等用例）。

### 4.2 类型 → JSON 映射（保守）

沿用「拿不准就转字符串」的策略（与 LLM 注册表返回类型的保守映射同思路）：

| 源类型 | JSON |
|---|---|
| 整数族（int2/4/8、TINYINT…） | number |
| 浮点 / real / double | number |
| bool | true/false |
| text / varchar / char / uuid / date / timestamp(tz) / numeric | **string** |
| json / jsonb | 原样嵌入（已是 JSON） |
| bytea / blob | base64 string |
| NULL | null |
| 其余一切 | 转字符串；转不动则 null |

`numeric` 明确走 string 而非 number：JSON number 是 f64，会丢精度，
而 numeric 常用于金额（`项目/健身房`、`家有小奇/零钱` 都有）。

### 4.3 DDL 方言（推到迁移层）

主键自增三家写法互不兼容：

| | SQLite | PostgreSQL | MySQL |
|---|---|---|---|
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `SERIAL PRIMARY KEY` / `GENERATED … IDENTITY` | `INT AUTO_INCREMENT PRIMARY KEY` |
| 当前时间 | `datetime('now')` | `now()` | `NOW()` |
| upsert | `ON CONFLICT … DO UPDATE` | 同 | `ON DUPLICATE KEY UPDATE` |

**驱动层不管这些。** 在 `qi-web/迁移.qi` 上加一层极薄的建表助手：

```qi
建表(事务, "卡片", 自增主键("id") + 列("用户id", 整型) + 列("标题", 文本))
```

它按当前连接的后端产出对应方言。已有的 45 处裸 DDL **不强制迁移** ——
它们在 SQLite 上照常工作；只有当某个应用真要换 PG 时才改写那一处。

## 五、qi 侧新增（最小）

FFI 签名全部不变，只加两个只读函数供上层判方言：

```
数据库.后端(句柄) : 字符串       → "sqlite" / "postgres" / "mysql"
数据库.最后插入id(句柄) : 整数    → 统一 lastInsertRowid / RETURNING id / LAST_INSERT_ID()
```

第二个是必需的：SQLite 有 `last_insert_rowid()`，PG 必须 `INSERT … RETURNING id`，
MySQL 是 `LAST_INSERT_ID()` —— 现有 `仓储.qi` 的写路径依赖拿到新主键。

## 六、实施切片

| 阶段 | 内容 | 规模 | 验收 |
|---|---|---|---|
| **S1** | 后端枚举 + URL 分发 + PG 连接/执行/查询/参数化 + `?`→`$n` + 类型映射 | 中（~500 行 Rust） | 起 PG 容器，`项目/看板` 全套 CRUD 跑通 |
| **S2** | 事务（两套 API）+ `最后插入id` + `后端` | 小 | `项目/家安电器/资金事务测试.qi` 在 PG 上通过 |
| **S3** | MySQL 后端 | 小（S1 的模式复用） | 同 S1 用例换 MySQL |
| **S4** | 连接池（PG/MySQL 是网络连接，比 SQLite 更需要） | 中 | 压测：qi-web 并发下不耗尽连接 |
| **S5** | `迁移.qi` 建表助手（方言 DDL） | 中 | 一份迁移在三个后端建出等价表 |

S1+S2 即可宣布「qi 能用 Postgres」。S4 之前用「每连接一个 `Client`」的现状语义
（应用侧本来就是启动时连一次、全局复用）。

---

## 七、明确不做

- **不做 ORM/实体映射的扩展** —— `仓储.qi` 已经够用，本设计只换它脚下的地基。
- **不做异步数据库 API** —— 与现有阻塞 FFI 和协程调度的交互是另一个课题。
- **不做编译期 SQL 校验**（见原则 5）。
- **暂不做纯 qi 驱动**。PG wire protocol 是开放稳定的，pgx / rust-postgres 都是
  纯语言实现不链 libpq，用纯 qi 写 `qi-pg` 意识形态上最一致；但它需要
  SCRAM-SHA-256 认证、二进制/文本两种结果格式、类型 OID 表。
  （TLS 这一条**已不再是障碍** —— 2026-08-10 客户端 TLS 已落地，见
  `qi-runtime/src/io/tls_client.rs`，wss 与百炼实时端点实测通过。
  那份实现与 WebSocket 解耦，数据库/其它 TCP 客户端可直接复用。）
  本设计把接口按 JDBC/PDO 的形状定死，将来换纯 qi 实现时接口不变 ——
  这正是分层的意义。

## 八、风险

| 风险 | 影响 | 对策 |
|---|---|---|
| `?`→`$n` 改写在边角 SQL 上出错 | 静默查错数据 | 单元测试覆盖字符串/注释/`::`/jsonb 运算符；改写失败宁可报错不猜 |
| PG 无类型 `NULL` 参数报错 | 参数化写入失败 | 参数 JSON 的 null 显式绑 `Option<&str>`，必要时 SQL 侧 `$1::text` |
| 编译期与体积 | 二进制变大 | PG/MySQL 后端放 cargo feature，默认开；只要 SQLite 的场景可关 |
| 两份 database_ffi 漂移 | 行为不一致 | 已是 `include!` 共享，本设计不引入第二份 |

## 九、开发用的常驻测试库

多后端的正确性没法只靠单元测试 —— 占位符改写、类型降级、事务语义都要连真库才知道。
`qi/scripts/测试库.sh` 管着两个常驻容器（数据在命名卷、机器重启自动回来、只绑 127.0.0.1）：

```bash
./qi/scripts/测试库.sh 起      # 建/启动（幂等）
./qi/scripts/测试库.sh 状态    # 看就绪状态 + 连接串
./qi/scripts/测试库.sh 停/删
```

| | 镜像 | 端口 | 连接串 |
|---|---|---|---|
| PostgreSQL | postgres:17-alpine | 45432 | `postgres://qi:qidev@127.0.0.1:45432/qi_dev` |
| MySQL | mysql:8.4 | 43306 | `mysql://qi:qidev@127.0.0.1:43306/qi_dev` |

端口避开 5432/3306 是因为本机常有别的项目占着（实测 5432 被另一个项目的 PG 占用）。
口令是写死的开发口令，所以**只绑 127.0.0.1**，绝不能露到局域网。
